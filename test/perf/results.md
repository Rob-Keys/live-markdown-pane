# Local performance observations

These are development samples, not release sign-off. The test host was VS Code 1.140.0 on macOS 25.6, Apple M1 Pro, 16 GiB RAM. The extension was installed from the 0.1.0 VSIX in an isolated profile with user extensions disabled; VS Code built-in extensions remained available. Fixtures were local files in an untrusted workspace. The tests used CDP `Input.insertText` at 35 ms intervals, with 100 samples per fixture. Several sequentially opened fixture tabs remained open and hidden during later runs.

`input → frame 1` and `input → frame 2` are animation-frame timing proxies. They do not prove when pixels reached the display. Host acknowledgment runs through the local VS Code extension host and `WorkspaceEdit`. The long-task observer supports the Chromium `longtask` entry type; zero means it observed no task over 50 ms during the measured input window.

A temporary opener extension was enabled to open disposable Markdown files; only the current Live Markdown VSIX and VS Code built-ins were otherwise available. Each fixture received 100 one-character edits at 35 ms intervals. Earlier fixture tabs remained open and hidden as later fixtures were measured. The long-task observer reported zero tasks over 50 ms for every run.

After switching local acknowledgements to version-only messages and batching durable recovery snapshots, the current VSIX was installed into a fresh isolated VS Code 1.140.0 profile and measured on a 102,400-byte paragraph fixture. With 100 one-character inputs at 35 ms intervals, all 100 edits were matched to 100 host acknowledgements: frame-1 p95 4.6 ms, frame-2 p95 8.5 ms, input-to-acknowledgement p95 15.6 ms, durable-recovery wait p95 3.79 ms, host preparation p95 0.038 ms, and `WorkspaceEdit` wait p95 1.90 ms. No task over 50 ms was observed. This meets the local timing targets for the sampled fixture; animation-frame callbacks remain paint proxies, and the native-editor comparison was not repeated for this build.

A compositor-output diagnostic uses Chromium's workbench-page CDP screencast. An earlier version measured Node-side event arrival, which includes the input-binding, capture, and transport delays; it is retained only as a transport diagnostic. The sampler now starts at webview `beforeinput`, before CodeMirror handles the edit, aligns that time to the CDP screencast frame-swap timestamp with `performance.timeOrigin`, and reports event arrival separately. CDP documents the metadata timestamp as a frame-swap timestamp in the [Page protocol](https://chromedevtools.github.io/devtools-protocol/tot/Page/#type-ScreencastFrameMetadata). It does not measure photons at the physical display.

In VS Code 1.140.0 on the Apple M1 Pro, a fresh isolated profile and clean 102,400-byte plain-paragraph fixture received 100 one-character edits at 35 ms intervals. The first run's input-to-frame-swap p95 was 27.22 ms (p50 5.76 ms, max 214.72 ms); the frame-1 and frame-2 callback proxy p95s were 5.2 ms and 15.1 ms, host acknowledgement p95 was 11.7 ms, and no task over 50 ms was observed. This initial run does not meet the 16 ms frame-swap target. A second 100-edit run in the warmed profile on the same document measured 7.03 ms p95 to frame swap (p50 2.05 ms, max 16.17 ms); callback proxy p95s were 3.9 ms and 8.6 ms, host acknowledgement p95 was 15.7 ms, and no task over 50 ms was observed. This warm sample meets the local p95 frame-swap target for this fixture, but does not cover a cold open or the native-editor comparison. Both runs used JPEG screencast capture at 960×600, quality 40.

A separate formatting probe started from a clean 102,400-byte fixture and inserted 100 bold spans (`**LiveFormatProbe** `) at 35 ms intervals. All 100 edits produced a visible `.lm-strong` DOM mark, compositor frame, and host acknowledgement. Beforeinput-to-mark p95 was 4.0 ms; beforeinput-to-the-following-compositor-frame-swap p95 was 12.19 ms (p50 10.62 ms, max 14.52 ms). Host acknowledgement p95 was 10.9 ms and no task over 50 ms was observed. This formatting sample meets the 50 ms target on this fixture; physical display output remains unmeasured.

A warm-process native comparison was attempted in isolated VS Code 1.140.0 profiles on the Apple M1 Pro using independently generated 102,400-byte paragraph fixtures. CDP reported 100 insert dispatches and 100 compositor matches in both profiles, but an experimental visible-source DOM observer captured only 99 source mutations in the clean Live Markdown run and 4 of 5 in native smoke runs. Those old compositor values are invalid and remain excluded. The native editor also suppresses most `input` events for CDP-inserted text. A stricter paired harness and a five-sample setup check are documented below.

The paired benchmark harness was tightened to wait for its renderer-side pre-dispatch snapshot, observe mutations on the active editor surface, and run asynchronously so the Live Markdown extension host remains responsive. It then passed a five-input smoke run on VS Code 1.140.0 / macOS 25.6 / Apple M1 Pro with fresh profiles and the same 102,400-byte fixture. All 5/5 inserts in each profile were verified as visible source DOM mutations and matched to compositor frame swaps. Pre-dispatch-to-source-mutation p95 was 12.5 ms native and 19.9 ms Live Markdown; pre-dispatch-to-frame-swap p95 was 15.8 ms and 26.5 ms respectively. This validates the harness and visible-change gate only: five samples do not meet the 100-sample design requirement, the start includes CDP dispatch time, and compositor timestamps do not prove physical display output.

The default paired coordinator then completed three 100-sample runs on the same VS Code 1.140.0 / macOS 25.6 / Apple M1 Pro setup, using fresh profiles and one 102,400-byte fixture. Each run verified 100/100 visible source mutations and frame matches for both editors. Native source-mutation p95s were 10.6, 10.2, and 9.9 ms; Live Markdown was 11.3, 11.3, and 11.1 ms. Native compositor frame-swap p95s were 15.07, 14.77, and 14.66 ms; Live Markdown was 17.40, 16.18, and 51.21 ms. Live Markdown host-acknowledgment p95s were 18.7, 20.8, and 19.0 ms, with extension-host edit-preparation p95 below 0.029 ms in all three. The post-optimization run observed no task over 50 ms, but its frame-swap tail was highly variable. The workbench was brought forward through CDP; OS-level foreground focus was not independently verified. These results do not prove the ≤16 ms paint gate: visible DOM updates are under 16 ms, but screencast frame-swap timing varies and is not physical-display evidence.

After indexing only the Markdown blocks that contain the cursor, the paired 100-sample harness was run three more times on VS Code 1.140.0 / macOS 25.6 / Apple M1 Pro with fresh profiles and the same 102,400-byte fixture. Every run verified 100/100 visible source mutations and compositor matches for native and Live Markdown; none observed a task over 50 ms. Native visible-source p95s were 10.6, 10.1, and 10.1 ms, with frame-swap p95s of 15.41, 15.06, and 14.98 ms. Live Markdown visible-source p95s were 20.6, 11.3, and 11.6 ms; second-animation-frame proxy p95s were 16.1, 11.4, and 11.5 ms; frame-swap p95s were 54.15, 16.01, and 16.06 ms. Corresponding screencast-event-arrival p95s, which include capture and transport, were 60.5, 19.6, and 20.4 ms. Host-acknowledgment p95s were 38.4, 23.4, and 19.4 ms, while edit-preparation p95 stayed below 0.041 ms. Two repeats are near the 16 ms target, but one run's large tail means the local paint gate remains variable and unproven. CDP brought the workbench page forward, but OS-level focus and physical display output were not measured.

Two earlier 100-open CLI probes were retracted on 2026-10-05. The repeatable probe now samples the isolated VS Code process tree once per second through blank, open, and closed phases. On 2026-10-05, a fresh VS Code 1.140.0 profile opened 200 documents of 3,641 bytes each. Blank phase: 8 samples, 9 processes, RSS p50 669.7 MiB and range 641.9–1,024.4 MiB. ## Packaged runtime smoke checks

- The rebuilt 0.1.0 VSIX was installed in an isolated VS Code 1.140.0 profile and opened a distinct 66-byte Markdown fixture as a Live Markdown webview with an editable CodeMirror surface. This one launch sample measured 565 ms from tab activation to editable readiness and 1,046 ms to the next captured compositor frame. It confirms packaged activation; one small fixture is not a p95 performance result, and the frame swap is not physical-display confirmation.
- A 5,242,881-byte document opened with an editable CodeMirror surface, the large-file source-mode explanation, and no heading decorations.
- A 1,116,231-byte document stayed editable and showed its Markdown source; no table or image widgets were present in the rendered viewport.
- A small widget document rendered its task, table, and missing-image alt label. Clicking a table cell exposed the source row and returned focus to CodeMirror. Toggling the checkbox changed `[ ]` to `[x]`; Cmd+Z and Cmd+Shift+Z reversed and restored the source, and Cmd+S persisted `[x]` in the disposable fixture.
- In the repackaged VSIX, inline, reference-style, and autolink destinations appeared as link nodes inside a rendered table. A synthetic Cmd-click on the document-relative link opened its local target through VS Code while leaving the table rendered; an unmodified click on that link revealed the Markdown row for source editing. The isolated window was backgrounded, so visibility was emulated for this interaction check.
- The webview accessibility tree exposed the editor as a named textbox, the task as a labeled checkbox, the rendered table as a labeled group with column headers and cells, and the missing image as a labeled button. With `syntaxVisibility: "always"`, the document stayed editable, exposed literal Markdown, and removed task, table, and image widgets. This is an accessibility-tree check, not a VoiceOver test.
- In Chromium media emulation, `forced-colors: active` and `prefers-reduced-motion: reduce` both matched while the editor remained editable with task, table, and image widgets present. The forced-colors stylesheet resolved to a black canvas, white editor text and table borders, and the reduced-motion stylesheet resolved document scrolling to `auto`. This checks CSS behavior in browser emulation, not operating-system high-contrast mode or assistive technology.
- An integration check registered a writable non-file `FileSystemProvider`, opened its Markdown URI in the Live Markdown custom editor, edited it through the webview, and saved the change back through the provider. A separate real Remote-SSH round trip used VS Code 1.85.0 on macOS and a Debian 12 x64 Docker host: the packaged VSIX was installed into the remote extension host, `/workspace/remote.md` opened in the rendered editor, text was appended and saved, and a subsequent SSH `cat` verified the exact remote file contents. This verifies one real SSH-backed workspace configuration; WSL and other remote host configurations remain unverified.
- A rename regression check opened one document in two custom-editor groups, renamed it, closed one view, then applied an external edit and continued editing and saving in the remaining view. The shared bridge now follows `TextDocument` identity across URI changes. The provider also skips panels disposed during its asynchronous writability check.
- A source-mode stress run used a 6,200,017-byte single-line fixture, 100 one-character inputs at 35 ms intervals, and a 30-second acknowledgement window in an isolated VS Code 1.140.0 Extension Development Host. The revision-aware sampler matched all 100 input changes to 68 host acknowledgements. Frame-1 p95 was 1.5 ms, frame-2 p95 9.0 ms, input-to-acknowledgement p95 124.8 ms, durable-recovery wait p95 0.056 ms (max 51.0 ms), extension-host preparation p95 0.412 ms, and VS Code `WorkspaceEdit` wait p95 8.60 ms. It observed no task over 50 ms. This is diagnostic because the fixture exceeds the 5 MiB source-mode threshold; the design's 100 ms acknowledgement target is specified for 100 KiB documents. The prior FIFO sampler misattributed batched acknowledgements and reported 1,371.2 ms; that figure is superseded. Before batched recovery snapshots, the same-sized probe measured 4,360 ms p95 waiting for recovery writes.
